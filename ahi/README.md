# ZZ9000AX audio

`zz9000ax.audio` is the AHI subdriver for ZZ9000AX PCM playback and, when the
firmware exposes its receive capability, stereo RCA recording. It sends one
16-bit stereo stream to the card after AHI has mixed the application's
channels, and in its two hardware mixing modes it hands the channels to the
card's voice engine instead. `mhizz9000.library` is a separate MHI library
for the card's MP3 decoder.

| Component | Artifact | Installed to | Purpose |
|---|---|---|---|
| AHI subdriver | `zz9000ax.audio` | `Devs:AHI/` | PCM playback and capability-gated RCA recording. |
| AHI mode | `ZZ9000AX` | `Devs:AudioModes/` | Mode file generated by the AHI build. |
| MHI library | `mhizz9000.library` | `Libs:MHI/` | Hardware MP3 decoding for MHI-aware players. |

The current AHI driver identifies itself as `ZZ9000AX 4.33 (22.11.2026)`.
Build and installation instructions are in the [main README](../README.md).

## Set up AHI playback

1. Install `zz9000ax.audio` and the `ZZ9000AX` AudioMode file in the paths
   above.
2. Open AHI Prefs, select `ZZ9000AX`, then select a mix rate and channel
   count for the machine.
3. Save the AHI setting and select the mode in the application.

The driver advertises these AHI properties:

| Property | Value |
|---|---|
| Sample format | 16-bit signed stereo PCM |
| Mix rates | 8000, 12000, 24000, 32000, 44100, and 48000 Hz |
| AHI flags | `AHISF_KNOWSTEREO` and `AHISF_MIXING`; `AHISF_CANRECORD` when recording is available |
| Realtime attribute | `AHIDB_Realtime` is true |
| Playback buffer limit | 960 sample frames at 48 kHz (`AHIDB_MaxPlaySamples`) |
| Output | One output, `OUT 1` |
| Mixing ceiling | 8 channels (`AHIDB_MaxChannels`) |
| Hardware mixing | Two modes, `$CAFE0002` and `$CAFE0003`, in which the card mixes up to 32 channels; see below |

`AHISF_MIXING` means `ahi.device` performs linear interpolation and 32-bit
accumulation on the Amiga CPU. The card receives the final stereo stream, so
channel count is a CPU limit rather than a transport limit. The software modes
`$CAFE0000` and `$CAFE0001` call `PlayerFunc` at `ahiac_PlayerFreq` (16.16 Hz),
reading it after each call so tempo changes apply to the next mixed interval.
Fractional frames carry between ticks. Transport remains in 20 ms periods:
ticks can subdivide a period or span several periods, with each `MixerFunc`
call bounded by the playback buffer limit. There is no lower player-frequency
limit; the upper limit is one tick per source frame (the mix rate in Hz).
Clients must keep `AHIA_PlayerFreq` within their promised
`AHIA_MinPlayerFreq` and `AHIA_MaxPlayerFreq`. A zero frequency uses 50 Hz;
values above the source-frame limit are capped to it.

Use only the channels the machine can mix in time. The driver source recommends
2–4 channels at 44.1 or 48 kHz on a 68030 and advertises up to 8 for
68040-class machines. A 68060 or Apollo core can use 8 channels. When the AHI
CPU limiter skips a period, the result is audible stutter. Silent channels use
AHI's silence path.

## Hardware mixing modes

AHI lists two more ZZ9000AX modes: `ZZ9000AX:Hardware mixing, 32 voices`
(`$CAFE0002`) and `ZZ9000AX:Hardware mixing, 32 voices, interpolated`
(`$CAFE0003`). In these modes `ahi.device` mixes nothing. The driver maps each
AHI channel to a voice of the card's wavetable voice engine, so the channel
count costs no mixing time on the 68k: the 68k work is the channel model, one
small update per pass boundary of a voice, so a looping sound costs an update
per loop pass and nothing per output frame. The model is built for 68020 to
68060 (`-m68020-60`) and keeps the 64-bit multiplies and divides, which the
68060 does not execute, off that path.

The modes are for programs that set a sound, a frequency and a volume on each
channel: HippoPlayer's module players, DeliTracker 2 with the AHI NotePlayer,
and trackers. They need firmware that advertises the voice engine and
`zz9k.library` revision 42 or newer.

| Property | Value |
|---|---|
| Channels | Up to 32, one engine voice each |
| Rate | 48000 Hz |
| Sounds | `AHIST_M8S`, `AHIST_M16S`, `AHIST_S8S` and `AHIST_S16S`, copied to the card once at `AHI_LoadSound` |
| Effects | `AHIET_MASTERVOLUME` and `AHIET_CHANNELINFO`; any other returns `AHIE_UNKNOWN` |
| Latency | At least 160 ms, the engine's lead. `PlayerFunc` and `SoundFunc` run 160 to 320 ms ahead of the sound. |
| Recording | None |

Limits:

- Streaming clients do not work in these modes. Play16, ZZPlay's AHI output
  and the sound datatype load every buffer as `AHIST_DYNAMICSAMPLE`, which
  fails with `AHIE_BADSOUNDTYPE`. They use the 16 bit Stereo modes.
- One voice session runs at a time. `zz9k-voiceplay` and a hardware mixing
  mode cannot play together; the second one is refused.
- A Zorro II card is refused until firmware advertises the voice engine there.
- The anti-click smoothing of immediate changes is not reproduced.

```text
setenv ZZ9K_AHI_BANK 16384   ; sample bank in KiB, default 16384
setenv ZZ9K_AHI_LEAD 9600    ; lead in 48 kHz frames, default 0, the firmware floor
```

When a hardware mixing session closes, the driver writes
`ENV:ZZ9K_AHI_VOICE_STATS`. It holds the engine counters `late`, `rejected`,
`underruns` and `dropped`, then the driver's `ringfull`, `ticks`, `frames`,
`resyncs`, `fifodrops`, `recorddrops` and `overload`. A clean run has zeros
everywhere except `ticks` and `frames`.

The call-by-call mapping is in the
[hardware mixing specification](../docs/ahi-voice-mixing-spec.md).
[`ZZAXVoiceTest`](voicetest/README.md) plays ten scenarios through the modes
and prints the stats line; send that line with any problem report. Two tests
run without a card: `make ahi-voice-tests` checks the driver's channel model
against the firmware's engine source on the host, and
`ahi/driver/voice_worker_test.c` runs the worker's steps under vamos with a
fake voice session (build commands in its header comment).

## Record from RCA

Recording is available only when the card reports both the AX-present bit and
the receive-status capability. In that case the driver advertises
`AHIDB_Record`, `AHIDB_FullDuplex`, one input named `RCA In`, and up to 960
recording frames through `AHIDB_MaxRecordSamples`.

1. Connect the stereo source to the ZZ9000AX RCA inputs.
2. Set both ZZ9000AX auxiliary jumpers to `IN`.
3. Select `RCA In` in the recording application and select an AHI rate.
4. Start recording, or start recording and playback together from the same
   low-level AHI control.

Capture samples are `AHIST_S16S`. The input gain is fixed at `0x10000`;
`AHIC_InputGain_Query` returns that value when recording is available.
There is no monitor-volume or output-volume control. `AHIC_Input` accepts only
input index 0, `AHIC_Input_Query` returns 0, and `AHIC_MixFreq_Query` returns
the selected AHI rate.

Playback and recording can start and stop independently. Full duplex requires
`AHISF_PLAY | AHISF_RECORD` on one `AHIAudioCtrl`. A second low-level
`AllocAudio` owner cannot provide full duplex and is rejected.

Use [`ZZAXDuplexTest`](duplextest/README.md) to check the production
full-duplex path. It drives playback and recording through one `AHIAudioCtrl`;
two separate AHI clients do not exercise that path.

## AHI and MHI together

On a matched firmware and driver stack that advertises the audio fabric and
its rate capability, AHI acquires a fabric lease. The firmware converts and
mixes that lease with other fabric producers, so AHI PCM can play with MHI
music. The AHI mix-rate table stays available because the card converts the
source rate.

Without that fabric support, the legacy register path is used and AHI and MHI
are mutually exclusive. The driver detects the other owner's interrupt server
and rejects the allocation. AHI itself remains exclusive on both paths: one
`AllocAudio` owner at a time.

The legacy and fabric paths both pair every executed `PreTimer` with
`PostTimer`, including a CPU-limiter skip. The timer-pair fixture checks
recovery of complete, ordered PCM after an overload skip on both paths,
timer pairing without PCM delivery for oversized legacy periods, and player
cadence, fractional frame carry and ring wrap for changing player frequencies.
There is one timer pair per transport wake even when it contains several
mixer chunks. Skips still advance the player ticks.

## Firmware audio settings

With `zz9k.library` present and firmware advertising `ZZ9K_CAP_AUDIO_CONTROL`,
allocation submits the neutral source trim and release submits it again. The
firmware owns the master DSP chain, including LPF, mixer volume, and EQ. Use
ZZTop's Audio window to select scenes, set the Paula/AX baseline, and save
per-card clean ceilings.

On firmware without that capability, the driver uses legacy playback and sets
the low-pass filter to half the AHI mix rate, limited to 23900 Hz. A matched
firmware and driver pair is required for scene-owned audio settings and fabric
coexistence.

`MHIQuery(MHIQ_VOLUME_CONTROL)` advertises volume control only when matched
firmware advertises the audio control plane and the audio-stream gain service.
That control is per-stream attenuation below the active scene. MHI panning,
prefactor, and EQ calls are legacy controls; matched scene-authority firmware
reports them as unsupported rather than changing the shared DSP chain.

### Removed environment controls

| Identifier | Current behavior |
|---|---|
| `ENV:ZZ9K_MIX_LEVELS` | Ignored. The AHI and MHI drivers print a load-time debug notice when it exists. Set the baseline in ZZTop's Audio window instead. |
| `ENV:ZZ9000AX-NOLPF` | Ignored. Set the scene LPF in ZZTop's Audio window instead. |
| `AP_DSP_SET_VOLUMES` | Historical parameter used by the removed mix-level override. Current drivers do not use it for balance. |

The fallback ceilings for cards with no saved settings are Paula 48 and AX 80,
with a fallback baseline of Paula 36 and AX 72. They came from one Revision 1
card and do not establish a clean limit for another card. Saved ceilings and
baseline values take precedence. Recalibrate in ZZTop instead of raising a
ceiling to conceal distortion.

### Select the interrupt line

The driver uses INT6 (`INTB_EXTER`) by default. To use INT2 (`INTB_PORTS`),
create `ENV:ZZ9K_INT2` before the driver initializes:

```text
setenv ZZ9K_INT2 1
```

On firmware 2.3 or later, `int2 = on` in the SD card's `ZZ9000.CFG` selects
INT2 when `ENV:ZZ9K_INT2` is absent. The environment variable takes
precedence. Configure AHI and MHI the same way because their ownership check
looks at the selected interrupt list. Remove the environment variable when
migrating to the configuration-file setting.

## Hardware notes

Early ZZ9000AX Revision 1 boards have an opamp at U4 in the Paula
pass-through path. Its gain can make Paula much louder than AHI or MHI
playback. Later board revisions omit U4.

If an R1 board has this problem, desolder U4 only when equipped for SMD rework,
or set the card's clean ceilings and baseline in ZZTop. The recorded qualified
R1 pair was Paula 48 and AX 80. With the post-mix limiter, its boundary is 160;
the firmware caps each source at its own ceiling first. The former 60 boundary
for that pair predates the limiter.

## Troubleshooting

| Symptom | Action |
|---|---|
| Paula is much louder than MP3 or MOD audio | Check for an early R1 board with U4. Use the hardware repair above or calibrate the baseline and ceilings in ZZTop. |
| AHI output is muffled at low rates | On scene-authority firmware, raise the scene LPF cutoff in ZZTop. Legacy firmware uses the half-rate LPF setting. |
| ZZTop's Audio button is unavailable | The firmware does not advertise audio control, or the AX daughterboard is absent. Install the matched firmware for scene controls; playback can still work. |
| ZZTop reports `Audio: control state unavailable - retry` | Reopen Audio after the control service responds. The failed read changes no audio setting. |
| ZZTop reports `Calibration awaiting firmware state...` | Wait for the Audio window's retry, then close and reopen Audio if it remains pending. Audio edits and Save remain paused while the state is pending. |
| `Can't allocate! Hardware already used by MHI/AHI.` | Close the AHI or MHI client that owns the card. Legacy stacks allow one owner. |
| The audio device fails to open on a particular accelerator | Move both drivers to INT2 with `ENV:ZZ9K_INT2` or `int2 = on`. |
| A burst occurs before the first playback after boot | Use the current driver, which silences the DAC during allocation. |
| An AHI application has no recording option | Install firmware that reports receive status and the matching `zz9000ax.audio` driver. |
| Recording is silent | Set both auxiliary jumpers to `IN` and select `RCA In`. |
| `ZZ9000AX: hardware mixing refused: ...` on the debug channel | The line names the reason: firmware without the voice flag, `zz9k.library` older than revision 42, another voice client open, no card memory for the sample bank, or a Zorro II card. Use a 16 bit Stereo mode until it is fixed. |
| A streaming player fails to load sounds in a hardware mixing mode | Play16, ZZPlay AHI output and the datatypes need `AHIST_DYNAMICSAMPLE`, which these modes refuse with `AHIE_BADSOUNDTYPE`. Select `ZZ9000AX:16 bit Stereo` or `16 bit Stereo++` for them. |
| A tracker's pattern cursor runs ahead of the music in a hardware mixing mode | `PlayerFunc` runs one engine lead (160 ms or more) ahead of the sound there. This is by design; a lower lead needs the low-latency firmware work. |
| `ENV:ZZ9K_AHI_VOICE_STATS` shows `late` or `resyncs` above zero | The machine could not keep the driver's model ahead of the engine. Raise `ENV:ZZ9K_AHI_LEAD` or lower the load, and report the line. |

## Recorded qualification and history

| Record | Result or current constraint |
|---|---|
| Timer-pair fixture | The recorded emulator run used `amitools==0.8.1` and `machine68k==0.3.0`; its fabric recovery, legacy recovery, and oversized-legacy cases passed. The fixture controls scheduling, hook dispatch, and coherent RAM, so it does not qualify interrupt, DMA, cache, analog-return, or recording hardware. |
| Full duplex | [`ZZAXDuplexTest`](duplextest/README.md) is the hardware gate. It requires one low-level AHI allocation with playback and recording enabled together. |
| 4.28 | Added the `PreTimer` and `PostTimer` pairing that includes CPU-limiter skips. |
| 4.29 | Raised `AHIDB_MaxChannels` from 1 to 8. |
| 4.32 | Current driver identity and capability-gated recording/fabric implementation. |
| 4.33 | Added the hardware-mixing AudioModes (`$CAFE0002`, `$CAFE0003`): the card mixes up to 32 channels through its voice engine. Not yet qualified on hardware. |
| Unreleased | Software modes follow live `ahiac_PlayerFreq`, including tempo changes and fractional-frame intervals, on both legacy and fabric playback. The timer-pair fixture covers 60 to 25 Hz and 59.5 Hz over ten seconds. On the card, ZZAXVoiceTest S4 measured `PlayerFunc` within 0.25% of `AHIA_PlayerFreq` from 25 to 125 Hz in `$CAFE0000`. |
| Unreleased | Hardware-mixing modes: the 68k work per pass boundary no longer grows with the channel count and no longer uses 64-bit `mulu.l`/`divu.l` forms. `vm_walk` keeps the channels due before the walk limit in a heap, so a boundary costs one heap update instead of a scan of every channel (on ZZAXVoiceTest S2 with 32 voices a 20 ms tick has about 192 boundaries). The boundary arithmetic (`k * step`, the pass length) and the level math use exact 32-bit paths, and the driver is built with `-m68020-60`; before it used `-m68020`, whose inline 64-bit multiplies trap into `68060.library` on a 68060. Records, `SoundFunc` order and stamps are unchanged. On a 68060 the model's S2 tick fell from 7.0 ms to 2.6 ms of CPU time per 20 ms (4 voices: 351 to 160 us). Before, S2 left a priority-0 task about a sixth of the CPU in `$CAFE0002`, and in `$CAFE0003` the extra bus stalls while the card rendered took the 68k to 100%: the priority-110 worker kept the client from ever stopping the session, and the mouse froze. |
| Unreleased | Hardware-mixing modes: `AHI_LoadSound` sends its sample copy through the voice worker, the process that opened the voice session. Before, the copy ran in the client's task, the firmware refused it as a request from another client (status 5, `sample upload failed`), and every load returned `AHIE_UNKNOWN` on the card. The worker does not open `zz9k.library` itself: the library sends the Voice API calls as client 0 and `ZZ9KCall` as the caller's opener id, and only a task without an opener has one id for both. The worker copies one staging buffer per pass, so the session heartbeat continues during a large load. Start and the resync read the status again after the engine reset before they anchor the timeline; before, a Stop followed by Start counted its first records as `late` (13 in ZZAXVoiceTest S8). The worker harness models the library's client ids, the firmware's session ownership and the engine jump of a reset. |
| Hardware-mixing card run | A4000 with a 68060, ZZ9000 on Zorro III, AmigaOS 3.2, with this driver and firmware that renders one voice period per main-loop pass. ZZAXVoiceTest `SCENARIO ALL` passed 10 of 10 in `$CAFE0000`, `$CAFE0002` and `$CAFE0003`, with no `late`, underrun or resync in any session, and nothing wrong by ear. HippoPlayer 2.67 played 8, 16 and 32 channel modules in `$CAFE0002`; a 16 channel module played beside ZZPlay's MPEG-2 video with direct AX audio. Play16 in a hardware-mixing mode gets the `AHIST_DYNAMICSAMPLE` refusal on the debug channel. Zorro II is not qualified. |
